# How AI was used

**Tool:** Claude Code (agentic coding assistant running in the terminal / VS Code), working directly in this repo.
I directed the work, made the product calls and reviewed each step. The assistant planned, wrote code and tests, ran
them, and committed in small steps.

## Workflow

1. **Plan before code.** I gave the assistant the assessment brief (PDF) and the role (Python/React). It started in
   *plan mode*, which is read-only, and asked three decisions back to me:
   - Backend: FastAPI + SQLAlchemy (vs Django)
   - UI: React + Vite + MUI (vs AntD / Next.js)
   - Hosting: a single Docker service on Render

   It then wrote a plan (scope, architecture, test strategy, commit sequence) that I approved before any code was
   written.
2. **Requirements first.** The first commit is [REQUIREMENTS.md](REQUIREMENTS.md), as the brief asks.
3. **Vertical, test-backed increments.** Each commit is one slice (models → seed → CRUD → history → insights →
   export → UI → deploy). Tests were written with each slice and run before every commit, along with lint/format and
   typecheck.
4. **Run the real app.** Beyond the unit tests, the assistant built the SPA, served it through FastAPI on the seeded
   DB, and drove it in headless Chrome: search, open the drawer, edit a salary, see the history, open Insights. It
   then inspected the screenshots.

## Key prompts

- *"Here are my requirements [assessment PDF] … job role: Software Craftsperson / Python / React / AI – III."*
  This was the initial brief; everything else came out of the plan built from it.
- Plan-mode questions answered: **FastAPI + SQLAlchemy**, **React + Vite + MUI**, **Render (single Docker service)**.
- The assistant was also guided by a data-visualization skill for chart decisions:
  - one-hue single-series bars
  - no dual axes
  - a table view beside each chart
  - one hero number

## Where the AI was wrong, and how it was caught

Being explicit about this matters more than hiding it. Each issue was caught by a test, a tool, or by looking at the
running app, not by trusting the output.

| Issue | How it was caught | Fix |
|---|---|---|
| Timestamps came back **without timezone** (SQLite drops tzinfo), so the API returned naive datetimes after a reload | API test compared a GET response to the POST response | `UTCDateTime` type decorator that re-attaches UTC |
| **Median wrong for even counts.** SQLAlchemy 2 compiles `/` as true division, so the middle ranks were `2.5, 3` | Property-style test cross-checking SQL medians against `statistics.median` on generated data | Use `//` (integer division) |
| Alembic autogenerated a **NOT NULL column without a default**, which fails on a populated table | Review of the generated migration | Add nullable → backfill → tighten |
| A country change would **silently reinterpret salary in a new currency** | Thinking through the data model while writing salary history | New rule plus tests (API returns 422; the UI flags it before submit) |
| SQLite **WAL files were committed** (the `.gitignore` only covered `*.db`) | `git status` during a later commit | Untracked them, extended `.gitignore` |
| MUI select **out-of-range warning** when filters load from the URL before options arrive | Warning in test output, investigated rather than ignored | Keep the current URL value selectable while options load |
| **Clipped histogram labels** | Screenshot of the running app | Larger bottom margin |
| A first "fresh DB" container simulation **silently used the existing DB** (shell glob error aborted the env setup) | Sanity-checking the output | Re-ran with explicit env |

## Guardrails used throughout

- **Deterministic tests:** in-memory DB per test, fixed seeds, MSW for network, no sleeps.
- **Verifiable correctness claims:** the seed is a pure function; medians are cross-checked against Python; a
  migration test asserts the schema equals the models.
- **Lint, format and typecheck** run on every commit (ruff, prettier, tsc). CI runs them all, plus a container smoke
  test.
